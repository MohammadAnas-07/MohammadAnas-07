## Things I've built

### [Saga Fulfillment Engine](https://github.com/MohammadAnas-07/saga-fulfillment-engine)

**Distributed workflows get interesting when something fails halfway through.**

A distributed order fulfillment system that coordinates a multi-step workflow across services using the Saga pattern and Apache Kafka.

The project explores how services communicate asynchronously, how failed workflows can trigger compensating actions, and how distributed operations can be coordinated without relying on a single database transaction.

**Focus:** Java · Spring Boot · Microservices · Apache Kafka · Saga Pattern · Docker

### [Ledger Wallet API](https://github.com/MohammadAnas-07/ledger-wallet-api)

**Moving money between accounts requires more than a few API endpoints.**

A wallet and ledger API built around double-entry bookkeeping and transactional consistency.

It supports deposits, withdrawals, and transfers, with database locking to manage concurrent updates and idempotency keys to help prevent duplicate money movements. Kafka is used to publish transaction events.

The goal is to explore how backend systems can preserve correctness when multiple requests interact with the same financial data.

**Focus:** Java · Spring Boot · PostgreSQL · Apache Kafka · Transactions · Concurrency · Idempotency · Docker

## What I care about

**Correctness matters.**

An API returning a successful response doesn't automatically mean the underlying operation was correct. Data consistency, validation, and failure handling deserve attention.

**Concurrency changes everything.**

Code that works for one request may behave differently when multiple requests update the same resource at the same time. I want to get better at understanding and handling those cases.

**Distributed systems require failure thinking.**

Services can fail, messages can be duplicated, and workflows can stop halfway through. Designing for those possibilities is part of building reliable systems.

**Good engineering is about trade-offs.**

I want to understand why a particular architecture makes sense, what complexity it introduces, and when a simpler solution would be better.

**Building is how I learn.**

I learn best by implementing systems, investigating edge cases, reading documentation, and improving my understanding through practical work.
